# 운영 가이드

현재 배포된 프로토타입을 점검하는 방법과, `realtime-protocol.md` /
`claude-analysis.md`에서 정의한 권위 서버를 실제로 운영할 때 반드시 지켜야
할 원칙을 정리합니다. **이 문서의 상당 부분은 아직 존재하지 않는 서버를
대상으로 한 설계 원칙입니다.** 현재 상태와 향후 원칙을 절과 표로 구분해
둡니다.

## 1. 현재 배포 개념

배포 대상은 `music-quiz/`(`agent/codex` 브랜치) 하나뿐이며, 정적 UI
프로토타입입니다. 서버 코드나 게임 상태를 담당하는 백엔드는 없습니다.

- 빌드 산출물은 Cloudflare Workers 런타임을 대상으로 하는 `vinext build`로
  생성됩니다(`worker/index.ts`, `wrangler` 의존성 기준).
- `music-quiz/.openai/hosting.json`에는 `d1`/`r2` 바인딩이 모두 `null`로
  기록되어 있습니다 — 즉 지금 배포에는 데이터베이스나 오브젝트 스토리지가
  실제로 연결되어 있지 않습니다. `db/schema.ts`도 비어 있습니다.
- 배포 URL: <https://drop-the-beat-quiz.jyc686397.chatgpt.site> (비공개,
  접근 권한이 있는 계정 필요). 배포 자격 증명과 플랫폼 설정은 Codex가
  로컬에서 다루며 이 문서에는 포함하지 않습니다.

### 배포 상태 검증 명령

비밀값 없이 바깥에서 확인할 수 있는 최소 점검입니다.

```powershell
# HTTP 응답 코드와 헤더만 확인 (본문 다운로드 없이)
Invoke-WebRequest -Uri "https://drop-the-beat-quiz.jyc686397.chatgpt.site" -Method Head
```

- 비공개 배포이므로 로그인하지 않은 상태에서는 200이 아닌 응답(리다이렉트나
  인증 요구)이 정상일 수 있습니다.
- 실제 화면 확인은 브라우저로 로그인 후 접속해 대기실 화면이 뜨는지
  확인하는 것이 가장 확실합니다.
- 로컬 빌드 산출물을 검증하려면 `music-quiz/`에서 `npm.cmd run build` 후
  `npm.cmd test`(`tests/rendered-html.test.mjs`)를 실행합니다. 자세한
  명령은 [`DEVELOPMENT.md`](./DEVELOPMENT.md) §2 참고.

### 게임 서버 실행 (로컬)

```powershell
cd .worktrees\claude\server
npm.cmd start -- --songs ..\..\codex\data\songs.recovered.json --demo-clips --origin http://localhost:5173
```

시작하면 방 참여 코드와 방장 토큰을 출력합니다. `--demo-clips`는 음원 URL과 재생
구간이 비어 있는 곡에 자리표시자를 채워 라운드 흐름만 확인하게 해 주는 옵션이며,
**실제 소리는 나지 않습니다.** 이 옵션 없이 복구 데이터를 그대로 넣으면 171곡이
전부 `MISSING_MEDIA_URL`로 제외되어 게임을 시작할 수 없습니다.

`--origin`을 생략하면 Origin 검사가 꺼집니다. 로컬 개발에서만 생략하세요.

### 게임 서버 배포에 관한 중요한 제약

**현재 프런트엔드가 올라가 있는 Cloudflare Workers에는 이 서버를 그대로 올릴 수
없습니다.** Workers는 포트를 열고 연결을 기다리는 프로세스를 실행하지 않습니다.
`server/`는 `node:http`로 소켓을 직접 받는 일반 Node 프로세스입니다. 선택지는 둘
중 하나입니다.

| 방법 | 내용 | 비용 |
| --- | --- | --- |
| 장시간 실행 프로세스를 지원하는 호스트에 배포 | Node 22.13+ 가 돌고 WebSocket 업그레이드를 통과시키는 곳(VM, 컨테이너 등)에 그대로 올립니다. 코드 변경 없음 | 프런트와 서버가 서로 다른 곳에 배포되므로 CORS/Origin 설정과 도메인 정리가 필요합니다 |
| Cloudflare Durable Objects로 이식 | 방 하나 = Durable Object 하나. `gameRoom.ts`는 소켓을 모르는 순수 상태 기계라 그대로 옮겨갑니다. 새로 쓰는 것은 `websocket.ts`/`index.ts` 자리의 얇은 어댑터뿐입니다 | 전송 계층 재작성, 타이머를 Durable Object 알람으로 교체 |

엔진과 전송을 분리해 둔 이유가 이것입니다. 어느 쪽을 고르든 게임 규칙과 그 테스트
54개는 손대지 않습니다. 방 하나를 한 곳이 소유해야 한다는 §1-2의 제약은 두 방법
모두에 그대로 적용됩니다 — Durable Object는 그 제약을 플랫폼이 대신 지켜 줍니다.

## 2. 환경변수와 시크릿

- 현재 프로토타입은 필수 환경변수가 없습니다(D1/R2 바인딩이 비어 있고,
  외부 API 키를 쓰지 않습니다).
- 앞으로 미디어 URL 서명, 세션 토큰 서명 키 등을 추가할 때는 `.env`에만
  두고 저장소에는 값이 빈 `.env.example`만 커밋합니다.
- 방장 토큰(`HostToken`)과 참가자 세션 토큰(`PlayerToken`)은
  `claude-analysis.md` §5, §7에 따라 서버에서만 생성·검증하는 비밀값입니다.
  클라이언트 코드나 로그에 원문을 남기지 않습니다.

## 3. 헬스체크 · 로그 · 모니터링 (향후 서버 구현 시 원칙)

권위 서버가 구현되면 다음을 최소 기준으로 둡니다.

- **헬스체크**: 프로세스 생존 여부와 별개로, 활성 방 수·연결 소켓 수를
  노출하는 엔드포인트를 두어 "떠 있지만 방 상태가 깨진" 경우를 구분합니다.
- **로그**: 방 생성/종료, 방장 시작/일시정지/스킵, 라운드 승자 확정, 에러
  응답(`ERROR` 메시지 발송)을 최소한 로그에 남깁니다. 정답 문자열이나
  참가자 개인 식별 정보는 로그에 원문 그대로 남기지 않습니다.
- **모니터링 신호**: 방 하나당 소켓 연결 실패율, `ANSWER_REJECTED`
  급증(스팸 신호), 라운드 처리 지연(서버 수신 시각과 `deadline` 간 오차)을
  우선 관찰 대상으로 둡니다.

## 4. 재접속 · 장애 대응 (설계 원칙, `claude-analysis.md` §5 기준)

- 소켓이 끊겨도 서버는 참가자 점수와 방 슬롯을 즉시 삭제하지 않고
  `connected: false`로만 표시합니다. 재접속 시 저장된 세션 토큰으로
  본인 확인 후 전체 상태 스냅샷(`ROOM_STATE`)을 다시 보냅니다.
- 방장이 라운드 중 끊기면 서버가 자동으로 `ROUND_PAUSED`로 전환해 타이머를
  멈춥니다. 방장이 끝내 돌아오지 않는 경우에 대한 자동 복구(호스트 위임 등)는
  의도적으로 설계에 포함하지 않았습니다 — 캐주얼한 소규모 게임 범위를
  넘는 복잡도로 판단했기 때문입니다.
- 방 상태는 프로세스 인메모리에만 존재합니다. 서버 프로세스가 재시작되면
  진행 중이던 방은 모두 사라집니다. 이는 결함이 아니라 명시적으로 받아들인
  제약입니다(`claude-analysis.md` §8).

## 5. 서버 보안 원칙 (구현 시 반드시 지킬 것)

`claude-analysis.md` §7, `realtime-protocol.md` §2·§4에서 정의한 원칙을
운영 관점으로 요약합니다.

| 원칙 | 내용 |
| --- | --- |
| 방장 권한은 서버가 검증 | 모든 `HOST_*` 메시지는 서버가 `hostToken`을 방 상태와 대조해 검증합니다. "현재 연결된 소켓이 방장이겠지"라고 추정하지 않습니다. |
| 메시지 순서 보장 | 방 하나의 상태는 단일 프로세스가 소유하고 메시지를 순차 처리합니다(§2). 두 개의 "첫 정답" 판정이 동시에 성립하는 경쟁 상태를 분산 락 없이도 원천 차단합니다. |
| 정답 비노출 | `ROUND_START`에는 정답/별칭을 담지 않습니다. `toRoundPublicPayload`(`shared/songCatalog.ts`)가 공개 페이로드를 만드는 유일한 함수입니다. |
| 오답 비공개 | 오답은 제출한 본인에게만 통보합니다. 다른 참가자에게 오답을 브로드캐스트하지 않습니다 — 답 따라 적기를 막기 위해서입니다. |
| 입력 크기 제한 | 닉네임 길이 제한, 제어 문자 제거, 빈 닉네임 거부. 정답 제출 문자열 크기도 상한을 둡니다. |
| Rate limit | 참가자당 라운드당 정답 제출 횟수를 제한해 단순 스팸/플러딩을 막습니다. |
| Origin 검증 | WebSocket 업그레이드 요청의 `Origin` 헤더를 배포 도메인과 대조해 단순한 크로스사이트 소켓 하이재킹을 차단합니다. |
| 클라이언트 값 불신 | 점수, 순위, 타임스탬프는 항상 서버가 계산한 값을 유일한 사실로 취급합니다. 클라이언트가 보낸 시각이나 점수를 신뢰하지 않습니다. |

## 6. 백업 · 롤백 · 마이그레이션 원칙

- **백업**: 현재 서버는 상태를 인메모리에만 두므로 백업 대상 자체가
  없습니다. 영속 저장소(방 로그, 곡 카탈로그 등)를 추가하는 시점부터
  백업 정책을 정의해야 합니다.
- **곡 데이터**: `data/songs.recovered.json`과 운영자가 채운 완성본은
  버전 관리 대상입니다. 값을 덮어쓰기 전에 이전 버전을 커밋해 두면
  `DUPLICATE_ALIAS`/`NO_USABLE_ALIAS` 같은 회귀를 손쉽게 되돌릴 수 있습니다.
- **롤백**: 배포는 빌드 산출물 단위로 이루어지므로, 문제가 발견되면 직전
  정상 빌드로 재배포하는 것이 가장 단순한 롤백입니다. 배포 파이프라인
  자체의 자격 증명·조작은 Codex가 담당합니다.
- **마이그레이션**: `db:generate`(drizzle-kit)는 `db/schema.ts`가 비어 있는
  현재는 생성할 것이 없습니다. 실제 테이블을 추가하면 마이그레이션 파일을
  커밋하고, 적용 전 스테이징 환경에서 먼저 검증합니다.

## 7. 문제 해결

| 증상 | 원인 | 조치 |
| --- | --- | --- |
| 배포 URL이 로그인 화면만 보여준다 | 비공개 배포, 접근 권한 없음 | 권한이 있는 계정으로 로그인. 계정 발급은 Codex/배포 담당자에게 확인 |
| `npm.cmd run build` 실패 | Node.js 버전이 22.13.0 미만이거나 의존성 미설치 | `node --version` 확인 후 `npm.cmd install` 재실행 ([`DEVELOPMENT.md`](./DEVELOPMENT.md) §1 참고) |
| `npm.cmd test` 실패 | 빌드 산출물이 오래되었거나 `tests/rendered-html.test.mjs`가 기대하는 마크업이 바뀜 | 먼저 `npm.cmd run build`가 성공하는지 확인 후 실패한 assertion 확인 |
| 정답을 입력해도 항상 오답 처리된다(프로토타입) | 현재 UI는 첫 번째 곡(`Dynamite`)만 판정 대상 | 알려진 프로토타입 한계. [`USER_GUIDE.md`](./USER_GUIDE.md) §4-2 참고 |
| 여러 사람이 같은 방 코드로 들어가지 못한다 | 방 참여 기능과 서버가 아직 없음 | 알려진 미구현 항목. [`README.md`](../README.md)의 구현 현황 표 참고 |
| (향후 서버) 라운드가 시작되지 않는다 | 방장 토큰 검증 실패 또는 참가자 0명으로 `NOT_ENOUGH_PLAYERS` 거부 | 서버 `ERROR` 응답의 `reason`을 확인 (`realtime-protocol.md` §4) |
| (향후 서버) 같은 정답인데 서버는 오답, 클라이언트는 정답으로 판정한다 | 서버와 클라이언트가 서로 다른 정규화 로직을 사용 중 | `shared/answerMatching.ts` 하나만 양쪽이 import하도록 통일 (`integration-plan.md` §1.1) |

## 8. 출시 전 미완료 항목

### 완료된 항목

- **권위 WebSocket 서버** (`server/`) — `realtime-protocol.md` §4 전이표대로 구현,
  단위·종단 테스트 54개. 방 상태 기계, 서버 수신 시각 기준 선착순 판정, 방장 토큰
  검증, 참가자 세션 토큰 재접속, 오답 비공개, 정답 미노출, Origin 검증,
  라운드당 제출 횟수 제한을 포함합니다.
- 헬스 체크 엔드포인트 `GET /health` — 재생 가능 곡 수를 함께 반환합니다.
- 종료 절차 — `startServer()`가 돌려주는 `stop()`이 타이머를 정리하고 업그레이드된
  소켓까지 닫습니다. 업그레이드된 소켓은 `server.close()`로는 정리되지 않으므로
  이 경로를 쓰지 않으면 재배포가 무기한 대기합니다.

### 남은 항목

아래 항목이 모두 채워지기 전에는 "실제 온라인 멀티플레이 서비스"로 볼 수
없습니다.

- **방을 만드는 HTTP API** — 현재 방은 서버 코드에서 `game.createRoom()`으로만
  생성됩니다. 방장이 브라우저에서 방을 만들 수단이 없습니다.
- **UI와 서버 연결** — 프로토타입은 여전히 브라우저 안에서 자체 판정합니다.
- 방 상태 영속화 (현재는 프로세스 메모리에만 존재)
- 방 생성·참여 요청 빈도 제한 (라운드당 정답 제출 제한만 구현되어 있습니다)
- 라이선스가 확보된 음원 URL 등록 — SCX에서 오디오를 추출·재배포하는 것은
  이 프로젝트 범위가 아니며 허용되지 않습니다 ([`SONG_DATA_GUIDE.md`](./SONG_DATA_GUIDE.md) §1)
- 운영 인증(로그인/접근 제어를 넘어선 방장 신원 확인)과 관측성(로그·지표
  수집, §3의 헬스체크 엔드포인트)
